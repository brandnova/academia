    Long List Handling (Future)

    • [ ] Windowed "View more" lists (Facebook-style). The View more button stays, but only a fixed number of rows ever stay on the page. After the reader has loaded several pages, the oldest rows at the top are dropped from the page, however many times View more is clicked.

      Why: today every click appends a page and nothing is ever removed. After ten clicks a list holds 200 or more rows, which means a large DOM, a scrollbar thumb the size of a pixel, and sluggish scrolling on cheap phones, which this audience uses.

      Behaviour: - Keep a window of N pages (for example 3 pages of 20 rows). When appending another page would exceed it, the oldest page leaves the DOM and a spacer of the same total height takes its place, so the scroll position does not jump. - When the reader scrolls back up to the spacer, a "Show earlier questions" control brings the previous page back and drops a page from the bottom. It can be button-only at first. - Fetched pages stay in an in-memory map keyed by page number, so returning to an earlier page is instant and never refetches. A filter, search or sort change clears the window and the map. - Rows vary in height (the meta row wraps), so measure rows with ResizeObserver and sum the measured heights for the spacer, with an estimate for rows never measured.

      Plan, in this order: 1. Measure first, with 500 realistic rows (React Profiler, Lighthouse). 2. Try CSS only: content-visibility: auto with contain-intrinsic-size on each row skips rendering offscreen rows without removing them. Stop here if that is enough. 3. Build a shared usePagedList hook that owns fetch, append, the stale-response guard and the load-more error, which is logic now hand-copied across about a dozen components. Then a WindowedList wrapper that does the eviction. Adopting the hook is a clean-up on its own.

      Where: RecentQuestionsList, HubQuestionList, TagQuestionsClient, SearchResultsClient, the notifications page, the profile tabs, and the admin lists (users, schools, tags, reports, unanswered queue).

      Details to get right: - Accessibility: announce the position ("Showing 41 to 100 of 340") in a polite live region, never evict a row that holds keyboard focus, and keep the View more button reachable. - Browser find (Ctrl+F) only sees rows currently on the page, so say so. - Do not replay the stagger animation for rows brought back at the top. - Browser Back should restore position: keep the loaded pages and scroll offset in sessionStorage, keyed by route and filters. - The total count in the list header stays the API's count.

      Not goals: classic full-list virtualization, any new dependency, or any change to the API's pagination.

      Done when: after 500 rows are loaded by repeated View more, the DOM never holds more than N rows, scroll position does not jump on eviction, going back to earlier rows works without refetching, the position is announced, and a filter change resets the window.
